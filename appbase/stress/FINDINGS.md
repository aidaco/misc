# appbase SQLite multi-writer boundaries — measured findings

Generated by `stress/concurrency.py` on 2026-05-24.
Environment: SQLite 3.50.4, Python 3.14, appbase 0.0.1, 16 CPUs, Linux, local
SSD-backed `tmp`. appbase defaults: WAL, `synchronous=normal`,
`busy_timeout = timeout*1000` (30 s by default), `autocommit=True` (one
transaction per statement), `PRAGMA optimize` on connect *and* close.

Re-run with `uv run python stress/concurrency.py`. Absolute numbers move with
hardware; the **shapes and the failure modes** are what matter.

## TL;DR — the operating envelope

| Boundary | What happens at the edge | Caught by `busy_timeout`? | Caught by app retry? | Rule |
|---|---|---|---|---|
| **Write contention** | One writer at a time; ~12–18k tiny inserts/s ceiling regardless of writer count; contention shows up as **tail latency**, not failures | **Yes** — fully, up to 32 writers | Yes (but worse latency than busy_timeout) | Keep `busy_timeout`; add retry as a backstop. Concurrency buys no write throughput. |
| **Cold-connect storm** | Simultaneous *first* connects failed `database is locked` at **50–88%** — `PRAGMA optimize` (an ANALYZE write) lost a lock-upgrade race | **No** | **Yes** — retrying the connect → 0 failures | **Fixed**: `PRAGMA optimize` removed from `connect_raw` (it runs on close only), so `connect()` is now read-only and the storm reports 0 failures. |
| **WAL snapshot staleness** | A streaming read cursor held open across a write fails `database is locked` in **~0.03 ms** the instant another connection commits | **No** (bypassed by ~6 orders of magnitude) | **No** — every retry re-fails while the cursor is open | **Materialize the driving query before writing.** Never hold a read cursor open across writes. |
| **VACUUM under load** | `Database.vacuum()` waits out `busy_timeout` then fails `database is locked` | n/a (it *is* the lock) | n/a | Run `vacuum()` only in a maintenance window on an idle connection. |

The two boundaries that **no amount of `busy_timeout` or retry can save you from** —
snapshot staleness and the connect storm — are the ones to design around. Held-lock
contention, the one people worry about most, is the benign one here.

---

## 1. Write contention — `busy_timeout` turns failures into latency

300 single-row autocommit inserts per writer, 256 B payload, separate processes.

**`busy_timeout = 30 s` (appbase default):**

| writers | written | lock fails | rows/s | p50 ms | p99 ms | max ms |
|--:|--:|--:|--:|--:|--:|--:|
| 1  | 300  | 0 | 16,052 | 0.07 | 0.14  | 0.7   |
| 2  | 600  | 0 | 15,415 | 0.05 | 0.13  | 18.6  |
| 4  | 1200 | 0 | 12,421 | 0.07 | 3.36  | 33.9  |
| 8  | 2400 | 0 | 11,751 | 0.06 | 3.40  | 179.5 |
| 16 | 4800 | 0 | 18,270 | 0.03 | 8.44  | 179.4 |
| 32 | 9600 | 0 | 17,565 | 0.04 | 33.46 | 429.5 |

**`busy_timeout = 0`, no retry (the naked case):**

| writers | written | lock fails | fail % |
|--:|--:|--:|--:|
| 1  | 300 | 0    | 0.0  |
| 2  | 347 | 253  | 42.2 |
| 4  | 462 | 738  | 61.5 |
| 8  | 660 | 1740 | 72.5 |
| 16 | 857 | 3943 | 82.1 |
| 32 | 925 | 8675 | 90.4 |

**`busy_timeout = 0` + app `retry_on_locked`:** 0 failures at every writer count,
but max latency climbs to **2,122 ms** at 32 writers (vs **429 ms** for
`busy_timeout=30s`).

**Reading it:**
- SQLite serializes writers on one global write lock. Aggregate throughput is
  **flat at ~12–18k tiny inserts/s** from 1→32 writers — **adding writers buys
  no write throughput**, it only spreads the ceiling across more processes and
  grows the **tail** (p99 0.14 ms → 33 ms; max 0.7 ms → 429 ms).
- With the default 30 s `busy_timeout`, contention produced **zero** failures up
  to 32 writers. The failure boundary is far past any sane concurrency: you'd
  need queue-depth × per-write-time to exceed 30 s.
- Without `busy_timeout` *and* without retry, you fail **immediately and often**
  (42% at 2 writers, 90% at 32). This is exactly audiorotica's "write bursts
  without retry crashed immediately."
- `busy_timeout` and app-retry both eliminate failures, but **`busy_timeout`'s
  tail latency is ~5× lower** — SQLite's built-in busy handler polls far tighter
  than exponential backoff. So: rely on `busy_timeout` for held-lock contention;
  keep retry as a backstop for what busy_timeout can't cover (below), not as its
  replacement.

## 2. Cold-connect storm — `PRAGMA optimize` makes `connect()` a writer

All writers call `appbase.database.connect(...)` + open at the same instant,
against a fresh WAL database, `busy_timeout = 30 s`.

| simultaneous connects | connect() failures | fail % | failures w/ retry |
|--:|--:|--:|--:|
| 2  | 1  | 50 | 0 |
| 4  | 3  | 75 | 0 |
| 8  | 7  | 88 | 0 |
| 16 | 10 | 62 | 0 |
| 32 | 25 | 78 | 0 |
| 64 | 41 | 64 | 0 |

**Reading it:** This boundary was **not** seen in audiorotica (its writers
started staggered and were long-lived) — the harness surfaced it. The pragma
handshake in `connect_raw` ends with `PRAGMA optimize = 0x10002`, which runs
`ANALYZE` and **writes** `sqlite_stat1`. ANALYZE reads first, then upgrades to a
write lock; SQLite returns `SQLITE_BUSY` on a lock *upgrade* **immediately**
(deadlock avoidance) rather than invoking the busy handler — so `busy_timeout`
never engages. Probing the handshake pragma-by-pragma confirmed `optimize` is the
*only* statement that fails (18–28 of 32 across repeats). Even **two**
simultaneous first-connects have a ~50% chance one fails.

This bites any consumer that starts a pool of workers together (a process pool, a
parallel job launcher, N CLI invocations fired at once). Retrying the connect
clears it completely.

**Resolved (2026-05-24):** `PRAGMA optimize` was removed from `connect_raw` (it
already runs in `close_raw`, which is SQLite's recommended time). `connect()`'s
handshake is now read-only. Re-running this scenario reports **0 failures at
2→64 simultaneous connects** with no retry. Guarded by
`test_connect_does_not_write_under_concurrent_writer` and by this scenario (which
now expects 0 failures).

## 3. WAL snapshot staleness — the unrecoverable one

Two connections, `busy_timeout = 30,000 ms`. A failure far below 30,000 ms proves
`busy_timeout` is bypassed.

| read pattern | holder write | latency ms | |
|---|---|--:|---|
| streaming | **FAILED: database is locked** | **0.03** | cursor held open across the write |
| materialized | survived | 0.04 | read drained to a list first (the audiorotica fix) |
| streaming + retry(5) | **FAILED: database is locked** | 64.29 | retry burns its whole budget, still fails |

**Reading it:** This was audiorotica's actual root cause (CR2), reproduced
against appbase's real config. A streaming read cursor (`select().execute()`
iterated lazily) pins a WAL read snapshot on its connection. The moment **another
connection commits**, the holder's snapshot is stale, and its next write fails
`SQLITE_BUSY` **immediately** — ~0.03 ms against a 30,000 ms `busy_timeout`, i.e.
bypassed by ~6 orders of magnitude. **No retry recovers** it: the cursor stays
open, so every retry re-fails (the retry(5) row burned its budget and still
failed). The only fix is structural: **materialize the driving query
(`list(...)`) before writing in the loop**, which closes the read transaction.

## 4. VACUUM under a concurrent writer

A writer holds `BEGIN IMMEDIATE`; another connection calls `Database.vacuum()`
with `busy_timeout = 2 s`:

```
-> blocked then failed: database is locked  (after 2007 ms)
```

**Reading it:** `VACUUM` needs a database-wide exclusive lock, so it waits out the
full `busy_timeout` and then fails under any concurrent writer. Confirms the
existing guidance: routine reclamation already happens via
`PRAGMA incremental_vacuum` on close; call `vacuum()` only in a maintenance window
on an otherwise-idle connection.

## Recommendations

1. **(appbase) ~~Reconsider~~ DONE — `PRAGMA optimize` removed from `connect()`.**
   It was the only write in the connect handshake and made a cold-connect storm
   fail at 50–88% — a sharp edge for any consumer that starts workers together,
   and `busy_timeout` can't cover it. SQLite's own guidance is to run `optimize`
   on **close** (appbase already does) and periodically, not on open. Fixed by
   dropping it from `connect_raw`; re-measured at 0 failures (Scenario 2).
2. **(consumers) Keep the default `busy_timeout`.** It cleanly absorbs held-lock
   write contention up to at least 32 writers as a latency cost, never a failure.
3. **(consumers) Use `appbase.database.retry_on_locked` as a backstop, not a
   substitute** — wrap every write. (appbase now ships this helper.) It rescues
   the residual collisions `busy_timeout` misses, but costs more tail latency than
   `busy_timeout` and **cannot** fix snapshot staleness.
4. **(consumers) Never hold a streaming read cursor open across writes.**
   Materialize the driving query first. This is the one failure mode that is both
   silent under single-process testing and unrecoverable at runtime.
5. **(consumers) `vacuum()` is maintenance-window-only**, on an idle connection.
